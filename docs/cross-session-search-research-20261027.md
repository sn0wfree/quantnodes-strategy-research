> ## ⚠️ 已作废（2026-10-27，同日实测后推翻）
>
> 实测：真实库 5.34 MB / 83 会话 = **66 KB/会话**；文档中的 2GB 重开线需要
> **31,833 个会话**（每天 5 个 = 17.4 年，每天 20 个 = 4.4 年）。分库要解决的
> 膨胀问题当前不存在。
>
> 另：`messages` / `message_parts` 的 `FOREIGN KEY (session_id) REFERENCES

## 1. 先厘清一个此前没说清的事实

消息落库与事件流的关系，比前几轮讨论的更简单：

| 事实 | 证据 |
|---|---|
| `EventBusV2` 已退役 | `core/agent/event_store.py` 文档字符串：「Drop-in replacement for EventBus + EventBusV2」 |
| `EventStore.emit()` 是**唯一**事件发射点 | S1 已完成门面化；`slash_commands` 8 处、`service` 21 处、`chat` 若干处全部经它 |
| 消息事件只有两种 kind | `message_received`（用户）/ `assistant_message`（助手） |
| projector 从事件投影出 messages | `projection_handlers.py` 的 `_on_message_received` / `_on_assistant_message` |

**推论**：如果有人要「在消息写入时同步索引」，**只需要在 `EventStore.emit` 这一个点挂**——
比之前说的「persist_message + projector 两处」少一半。这打开了方案 F。

## 2. 六个方案（含新发现）

### A. 全局 search_index + 应用层同步
- 建 `platform.search_index` + FTS5，写消息后同步
- 前轮评估：约 1.7d，两个同步点（若挂在 emit 上则降为 1 个）
- 一致性：最终一致，可 rebuild
- **复杂度：中高**

### B. 搜索时遍历会话文件（当前选择）
- 每次搜索 fan-out 打开 N 个 per-session 文件，各自 FTS 查询后合并
- 复杂度：**最低**（无新表、无同步、无漂移）
- 一致性：**强**（永远读现状）
- 性能：O(会话数)；加三条约束后变成「有界延迟」
- **复杂度：低**

### C. 删除 `/search` 端点
- 前端零调用，代价最小
- 但丢能力、破契约
- **复杂度：无，但功能回退**

### D. 单库保留（放弃 per-session 拆分）
- 直接回到现状：所有会话一个文件，FTS 天然可用
- 但违背 P-2 定案（归档=移文件、单文件损坏隔离）
- **复杂度：无，但架构倒退**

### E. search_index 只存「消息引用 + 会话元数据」，内容走 blob 去重

- 建全局表 `search_ref(session_id, message_id, user_id, archived, content_hash)`
- **内容本体不复制**，按 hash 指向既有 blobs 表（P-1 已有内容寻址去重）
- 搜索流程：先查 FTS 得到 hash → 从 blobs 取内容渲染 snippet
- 优点：**存储零冗余**（实测消息内容仅 28KB，但长期增长时有意义）
- 缺点：FTS5 需要文本列才能建索引（`content=''` 的 contentless 表只存 token，不存原文）——
  实际上可以：contentless-delete 表只索引 token，命中后用 hash 回查 blobs 取原文
- **复杂度：中**（多一层 hash 间接）；**收益仅在大数据量时体现**——当前 28KB，不值得

### F（新发现）. 从事件流建索引：`EventStore.emit` 单点挂钩

- `EventStore.emit()` 已是唯一事件出口（S1 门面化成果）
- 在 emit 内对 `message_received` / `assistant_message` 两种 kind 追加一次索引写
- **只有一个同步点**，比 A 少一半代码
- 与 S3 天然衔接：S3 后 messages 完全由事件派生，索引也在事件上生成——**同一数据源**
- 缺点：emit 在每线程/每会话高频调用，索引写要保证不拖慢主路径（异步队列或失败容忍）
- **复杂度：中低**

## 3. 方案对比矩阵

| 方案 | 搜索可用 | 新消息可搜 | 一致性 | 附加存储 | 代码量 | 长期退化 | 架构影响 |
|---|---|---|---|---|---|---|---|
| A 全局索引（双点） | ✅ | ✅ | 最终 | 28KB+ | 高 | 无 | 引入派生索引 |
| **B 遍历文件** | ✅ | ✅ | **强** | 0 | **最低** | **线性** | 无 |
| C 删端点 | ❌ | ❌ | — | 0 | 无 | — | 功能回退 |
| D 放弃分库 | ✅ | ✅ | 强 | 0 | 无 | 无 | **架构倒退** |
| E hash 引用索引 | ✅ | ✅ | 最终 | 极小 | 中 | 无 | 引入派生索引 |
| **F emit 单点索引** | ✅ | ✅ | 最终 | 28KB+ | **中低** | 无 | 提前实现 S3 方向 |

## 4. 关键判断

### 4.1 B 的线性退化有多严重？（实测数据）

- 当前 83 会话 / 190 消息 → 全量扫描约 **几十毫秒**
- 若增长到 1000 会话 → 约 **0.5-1 秒**（每次 open 约 0.5ms × 1000）
- 加三条约束（倒序 + 搜够即停 + 上限 200）后 → **恒定几十毫秒**

**结论**：B 的实际退化可控，「慢」只发生在「用户真的需要搜遍全部历史」时。

### 4.2 F 的吸引力在哪

F 的真正价值不是「少写一个同步点」，而是**数据源统一**：
S3 之后 messages 完全从事件派生，索引也从事件派生——索引和正文永远同源。
而 A 方案里索引同步挂在「写 messages」上，S3 后 messages 是投影产物，同步点位置又要挪一次。

**但 F 有个硬问题**：`EventStore.emit` 是全系统最热的路径（每 token delta 都 emit）。
在里面加索引写，即使只对两种 kind 生效，也要做 kind 判断 + 跨库写。
必须**异步化**（队列 + 后台线程），否则每消息多一次同步跨库写会拖慢对话。

而异步化 = 引入「索引滞后窗口」+ 线程/队列生命周期管理 = 复杂度回升。

### 4.3 业界对照（已完成调研）

| 产品 | 布局 | 跨会话搜索 |
|---|---|---|
| SQLite 官方 | 推荐「每租户一文件」，并明确说跨文件要靠**应用层 fan-out** | 无内置 |
| Claude Code | **每会话一个 .jsonl** | **无全文搜索**（只有 `--resume` 选择器） |
| OpenCode | 单库 | 单库 FTS |
| LangGraph | 单库 checkpointer | SQL 查询 |

**业界事实**：采用「每会话一文件」的产品**都不做跨会话全文搜索**；做搜索的都保持单库。
我们选 B 等于「比业界多做一步」——用应用层 fan-out 弥补分库的代价。

## 5. 推荐

**维持 B（遍历），但补一个明确的升级触发器**：

```
现在：B（遍历 + 三条约束）
触发升级条件（任一）：
  - 实测搜索 P95 > 500ms
  - 会话数 > 500
  - 出现「需要搜索全部历史」的真实用户需求
升级目标：F（emit 单点索引，异步队列）
```

理由：
1. B 的复杂度最低、一致性最强、零维护成本；
2. 三条约束把「线性退化」变成「有界延迟」，实际体验可接受；
3. F 虽然方向正确（与 S3 同源），但需要异步化，是「为未来性能预付复杂度」；
4. 业界的「每会话一文件」产品根本不做这个功能——我们已经领先，不必一步到位。

**A 淘汰**（双点同步，且 S3 后要挪位置）；**E 淘汰**（28KB 的场景不值得 hash 间接层）；
**C/D 淘汰**（功能回退 / 架构倒退）。

## 6. B 的实现要点（落地清单）

1. **`search_sessions` 重写**：从全局库取用户会话（按 `updated_at` 倒序、排除 archived）
   → 逐个 `_session_db(sid)` 查 `messages_fts MATCH`
   → 合并排序、截断 limit；
2. **三条约束**：
   - 会话按 `updated_at` 倒序，凑够 `limit` 即停；
   - 单文件查询加 `LIMIT`；
   - 最多扫 200 个会话（可配置 `SR_SEARCH_MAX_SESSIONS`），响应带 `scanned` 字段；
3. **降级**：某会话文件损坏/缺失 → 跳过并计数，不整体失败；
4. **返回结构**：保持现状字段 + 新增 `scanned_sessions` / `truncated`（向后兼容）。

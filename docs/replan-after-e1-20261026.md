## 2. 重排理由

原计划前 6 天无可运行产物，而 pre-mortem 认定的最大风险是**单人长周期迁移中断**。E1 证明纯增量可行 → 改纵向切片：先打通一条真实路径，再横向加宽。**每个阶段结束都能安全停、能演示、都删掉了旧路。**

## 3. 修订后的阶段规划

### 阶段 1a · 纯 LLM 对话切片（2d）

**目标**：最小依赖验证新管线（房子能不能住人），不碰 AgentLoop。

- 最小 GraphEngine（包裹 langgraph）+ **llm 节点 only**（无工具、无 react）
- 最小 SessionController（准入 + 签发 turn_id/run_id）
- 一个入口接入

**验收**：跑一次真实对话，八站链路在事件流中完整可见；新旧路径输出对照。
**不抄近道**：mailbox/事件流/落位规则一个不少——最小是「功能最少」，不是「结构偷工」。
**风险**：langgraph 包裹不匹配 → 退回自研轻图（+1d）。此风险在依赖最少时暴露。

### 阶段 1b · react 节点 + 工具树（2d）

**目标**：把 AgentLoop 及其**整棵递归依赖树**（ToolRegistry→权限网关→subagent_tool→预算→压缩→skills）整体迁入 react 节点。

**为什么拆**：loop.py 的工具表里有 subagent_tool（递归起 AgentLoop）——依赖是闭环的，**没法只搬一半**；1a 先验证架构层，1b 的失败就收敛为纯接线问题。

**验收**：带工具的真实对话（如「跑个回测」真跑）；`test_steering_inbox.py` 等行为基线不破。

### 阶段 2 · 正确性基础 + 审计门 ①（4d）

| 项 | 说明 | 估 |
|---|---|---|
| **fence** | activeRunId 认领 + 提交校验；唯一无复用件 | 1d |
| ExecutorBridge + 进程池 | 四通道 + Windows Job Object + T3 第一段（写限/断网） | 2d |
| 预算运行中执行点 | 每次 LLM 调用前查余额 → budget_exhausted + CancelScope | 0.5d |
| **A5 不变量层** | 把散落的检查点收口到 `invariants.py`；不变量清单宣告（预计 6–8 条） | 0.5d |

**验收**：并行两研究 + 中途取消（连坐）+ 陈旧提交被拦——三场景各有测试；**不变量清单每条能指着代码说「执行点在这里且只有这里」**。
** endings：审计门 ①**（见 §5）。

### 阶段 3a · 入口迁移（4d）

**目标**：四个入口改走 WorkRequest（API → scheduler → CLI → MCP），逐个切换、逐个可回退。

**验收**：3a 末**轻量复查**（半小时）：四入口迁移后行为与旧路径一致（不算正式审计门，防止 3b 白做）。
**验收标准**：新增测试绿 + **受影响旧测试绿**（清单：`test_session*` ~15 个 · `test_api*` 子集）——不是全量绿（见 §4）。

### 阶段 3b · 数据面（3d）

**目标**：每 session 分库 + 全局小库 + SSE 单轨。

**验收**：事件写入分库、projector 按库工作、SSE 只剩一条轨。
**必须删除**：`_session_queues`、`sse_buffer.py`、`bridge_v2.py`。

### 阶段 4 · 清理与收敛 + 审计门 ②（7d）

| 项 | 说明 | 估 |
|---|---|---|
| **4 builder + 3 套 token 估算 → ContextHub** | 85% 复用；provider 试点 1 个先行 | 2d |
| 三处调度 → gateway/scheduler | 60% 复用 | 1d |
| 反向依赖 3 条消除 | — | 1d |
| 重复删除收尾 | steering inbox · seq_generator | 0.5d |
| **测试隔离修复** | 找共享状态源 + 清理夹具 + 乱序验证（此后「全量绿」才成立） | 1.5d |
| CI 门禁 + PROTOCOL_VERSION | gateway 零 FastAPI 由 CI 强制 | 1d |

**验收**：净删 >2000 行；全量测试**第一次真实全绿**；token 估算只剩一套。
**收尾：审计门 ②**（见 §5）。

## 4. 验收标准（修正版）

**每阶段：「新增测试绿 + 受影响旧测试绿」，附受影响清单——不承诺全量绿。**

原因：现有全量套件存在**顺序依赖**（合跑失败单跑通过，9/5 评估记录在案）——「全量绿」当前不可达，写了就是自欺；更危险的是天天误报的红会让真回归无人抬头。

| 阶段 | 受影响清单（预计） |
|---|---|
| 1a/1b | 新增为主；`test_chat_loop` 等对照 |
| 2 | `test_agent_budget` · `test_compact_*` · 新增 fence/executor |
| 3a/3b | `test_session*` · `test_sse_*` · `test_api*` 子集 |
| 4 | **全量**（隔离已修，此时全量绿才成立且有意义） |

## 5. 两个审计门 + 一个轻量复查

### 审计门 ①（阶段 2 末尾）
正确性机器全部就位、尚未大规模迁移——**修绕过漏洞最便宜的时机**（拖到阶段 3，坏模式会被四个入口复制）。
查：不变量收口彻底性（grep 绕过路径）· 契约实战检验（有无绕开 EntryPoint 直调内部）· 依赖方向人工查（CI 门禁未建前的替代）· 平移等价性抽查（新旧输出对照 ×3）· deprecated 标记健康度。
**产出**：HIGH/MED/LOW 发现清单 → 修复波 → 修复完才准进 3a。

### 轻量复查（3a 末，半小时）
四入口行为一致性确认——非正式门，防 3b 白做。

### 审计门 ②（阶段 4 末尾）
「旧债清零」的兑现核查——P1/P2 建在其上，不清点等于在未验收地基上盖二层。
查：删除清单逐条兑现（含孤儿测试）· **全量测试第一次真实全绿** · 原始 9 条发现销账（已闭/未闭/转 P1）· 性能基线建档（启动/增速/内存，作为 2GB/10GB 触发线起点）· T3 第一段实测（写限/断网真拦得住）· 文档对齐债清偿。
**产出**：销账清单 + 性能基线 + 文档修正 → 才准开 P1。

### 为什么阶段 1 末尾不设门
阶段 1 是故意做小的实验品——其质量由门 ① 连同阶段 2 一起覆盖。

## 8. 风险控制

| 风险 | 机制 |
|---|---|
| 切片绕过架构抄近道 | 硬性：1a 也必须走 mailbox/事件流/落位规则 |
| langgraph 包裹失败 | 1a 最早暴露；退路=自研轻图（+1d） |
| 新旧并存期变长 | 每阶段末尾删旧路径 = 验收标准之一 |
| 验收自欺 | 「受影响清单绿」替代「全量绿」；隔离修复后全量绿才恢复效力 |
| 单人中断 | 每阶段是可合入的完整单元，任何时刻停都不烂尾 |
| 检查点散落被复制 | 门 ① 在复制发生前收口不变量 |

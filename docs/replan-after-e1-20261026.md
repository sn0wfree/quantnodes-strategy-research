## 2. 重排理由

**原计划的问题**：E1 → 0.1–0.4 清旧债(4d) → A3 → A1 → A2 → A4 → A5 → E2–E5 → 门禁。前 6 天全部是「地基工作」，没有任何可运行、可演示的产出。pre-mortem 明确：最大风险不是设计，是**单人长周期迁移中断**。

**新原则**：纵向切片优先——先用最小成本打通「入口 → mailbox → 控制器 → 引擎 → 事件流」一条真实路径，证明架构能跑，再横向加宽。E1 已证明纯增量可行，切片是同一策略的延续。

## 3. 五阶段规划

### 阶段 1 · 最小垂直切片（3.5d）

**目标**：一条真实请求走完新架构；旧路径并存可对照。

| 内容 | 复用来源 | 估 |
|---|---|---|
| 最小 GraphEngine（包裹 langgraph，支持环） | `study/langgraph_engine.py` 用法参考 | 1.5d |
| chat preset（单 react 节点退化图）+ llm/react 节点 | `agent/loop.py` + `loop_stream.py`（90% 平移） | 1.5d |
| 最小 SessionController（准入 + 签发 turn_id/run_id，简化 7 阶段） | `service.py` 生命周期逻辑 | 0.5d |

**验收**：跑一次真实对话，事件流可见完整链路；`docs` 里记录新旧两条路径的对照输出。
**必须删除**：无（切片纯增量，但旧路径要标注 deprecated）。
**风险**：langgraph 包裹不匹配 → 退回自研轻图（+1d）。

### 阶段 2 · 正确性基础（3.5d）

**目标**：并发不出错——这是新架构能承载真实研究的前提。

| 内容 | 说明 | 估 |
|---|---|---|
| **fence**（A3） | activeRunId 认领 + 提交校验；唯一无复用件的核心件 | 1d |
| ExecutorBridge + 常驻进程池 | 四通道 + Windows Job Object + T3 第一段沙箱 | 2d |
| 预算运行中执行点 | ContextHub 前身：每次 LLM 调用前查余额 → budget_exhausted + CancelScope | 0.5d |

**验收**：并行两个研究、中途取消（子 agent 连坐）、陈旧提交被 fence 拦截——三个场景各有测试。
**必须删除**：无（旧路径仍在服务）。
**风险**：Windows Job Object/断网手段 → 已挂账，此处实测。

### 阶段 3 · 入口与数据收敛（7d）

**目标**：所有入口一条路；SSE 单轨；数据面分库。

| 内容 | 复用来源 | 估 |
|---|---|---|
| 其余入口迁移（API → scheduler → CLI → MCP） | 各入口现有逻辑改 adapter | 3.5d |
| 数据面分库（每 session 一库 + 全局小库） | `event_store.py` 接口保留 + `event_schema.py` 迁移模式 | 2d |

**验收**：四入口全走 WorkRequest；SSE 只剩一条轨；**删除** `_session_queues`、`sse_buffer.py`、`bridge_v2.py`。
**必须删除**：旧的 per-session 队列实现、SSE 双轨之一。
**风险**：入口迁移涉及面最广 → 逐入口切换、每个可独立回退。

## 5. 风险控制

| 风险 | 机制 |
|---|---|
| 最小切片被做成绕过架构的临时路 | 硬性：切片必须走 mailbox/事件流，落位规则不许破；fence 可在阶段 2 补但事件流不可省 |
| GraphEngine 包裹 langgraph 失败 | 阶段 1 早暴露；退路=自研轻图（+1d，原 AgentLoop 已足够简单） |
| 新旧并存期变长 | **每阶段末尾删除旧路径**纳入验收标准，不留给"以后" |
| 工期比原计划多 ~3d | 换取 4 个可演示里程碑 + 每阶段可回退；总账仍是"重组而非重写" |
| 单人中断 | 每阶段都是可合入的完整单元，任何一个阶段结束都能安全停 |

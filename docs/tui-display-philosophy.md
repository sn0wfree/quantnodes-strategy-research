# TUI 显示哲学设计原则

> **来源**: 从 vibe-trading 的 Rail/Live 显示模式中提炼，结合 QuantNodes-Research TUI 实践。
> **状态**: 活跃文档，作为后续所有 TUI 显示层改动的评审基准。

---

## 1. 核心原则

### 原则 1: 过程与记录分离

TUI 中存在两个性质完全不同的显示层，必须物理隔离：

| 层 | 职责 | 空间约束 | 内容完整性 | 更新方式 |
|---|---|---|---|---|
| **实时过程层** | 回答"现在在发生什么" | 有界（固定高度） | 可裁剪（仅显示尾部） | 原地替换 |
| **持久记录层** | 回答"之前发生了什么" | 无界（可滚动） | 完整保留，永不裁剪 | 追加写入 |

**关键约束**: 实时过程层中的任何裁剪（如只显示最后 N 行/N 字符）**仅作用于显示缓冲**，不得影响持久记录层的数据完整性。持久记录层始终拿到完整的原始文本。

**对应实现**:
- 实时过程层: `StreamingText` (Static widget, 有界高度, 原地更新)
- 持久记录层: `TranscriptView` (RichLog, 无 max_lines, 追加写入)
- 数据层: `ctx.history` (完整文本, 零丢弃)

### 原则 2: 折叠而非丢弃

当内容超出显示空间时，折叠（提供"还有更多"的指示 + 引导到完整视图），而非静默丢弃。

折叠指示器必须包含:
- 被隐藏内容的量级（`+N lines` / `+N chars`）
- 查看完整内容的途径（`scroll transcript for full` / 快捷键提示）

**反模式**: 直接 `text[-500:]` 而不告知用户内容被截断。

**正模式**:
```
↑ +847 chars (scroll transcript for full)
...最后几行可见内容...
```

### 原则 3: 流式更新是原地替换，不是追加

流式输出（LLM token delta）必须通过原地重绘整个区域来呈现，而非逐块追加新行。

**为什么**: 追加模式 (`write(chunk1); write(chunk2); write(chunk3)`) 会在日志组件中创建 3 个独立行，N 个 token = N 行，瞬间占满屏幕。原地替换模式 (`update(累积文本)`) 始终只有 1 个区域在变化，高度有界。

**刷新频率**: 实时过程层的重绘频率应受控（如每 40ms 一次或每帧一次），避免 flooding 消息队列。

### 原则 4: 状态切换有明确的生命周期

实时过程层的状态转换必须是显式的三阶段：

```
idle -> streaming -> idle
```

| 阶段 | 触发 | 显示 |
|---|---|---|
| idle (等待) | 用户提交输入 | ThinkingSpinner ("thinking... 1.2s") |
| streaming | 首 token 到达 | 隐藏 spinner, 显示 StreamingText, 原地更新 |
| idle (完成) | 流结束 | 隐藏 StreamingText, 完整文本写入 TranscriptView (1 条记录) |

**关键约束**: 流式结束后，实时过程层必须清空/隐藏，完整数据移交到持久记录层。不允许实时层残留过期内容。

## 2. 架构映射

```
┌─ StatusHeader ──────────────────────────────────────────┐
│ ● live  MiniMax-M3  12 msg  3 tools  ████░░ 2.1k/8k    │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─ TranscriptView (持久记录层) ───────────────────┐    │
│  │ [user] 研究A股低回撤量化策略                      │    │
│  │ [assistant] 完整回复文本...（可滚动查看全部）      │    │
│  │ ...                                              │    │
│  └──────────────────────────────────────────────────┘    │
│                                                         │
│  ┌─ StreamingText (实时过程层, 流式时可见) ─────────┐    │
│  │ ↑ +847 chars (scroll transcript for full)        │    │  ← 原地更新
│  │ ...最后几行可见内容...                            │    │
│  └──────────────────────────────────────────────────┘    │
│                                                         │
├─────────────────────────────────────────────────────────┤
│ > _                                                    │
├─────────────────────────────────────────────────────────┤
│ Ctrl+C halt  Ctrl+D quit  F1 help  Ctrl+L clear         │
└─────────────────────────────────────────────────────────┘
```

### 组件职责

| 组件 | 层 | 职责 |
|---|---|---|
| `ThinkingSpinner` | 实时过程层 | 等待首 token 时的 spinner |
| `StreamingText` | 实时过程层 | 流式输出原地更新区，有界高度，折叠指示器 |
| `TranscriptView` | 持久记录层 | 完整历史记录，无 max_lines，可滚动 |
| `ctx.history` | 数据层 | 完整的 user/assistant 对话历史 |

### 数据流

```
用户输入
  │
  ▼
ChatSession.dispatch()
  │
  ▼
stream_chat_to_tui()
  ├─ app.start_streaming()          ← 显示 StreamingText, 隐藏 spinner
  │
  ├─ async for chunk in astream():
  │     full_text += chunk.delta
  │     app.update_streaming(full_text)   ← 原地更新 (不创建新行)
  │
  ├─ app.end_streaming()            ← 隐藏 StreamingText
  │
  ├─ write(full_text)               ← 完整文本写入 TranscriptView (1条记录)
  │
  └─ ctx.history.append(full_text)  ← 完整文本写入数据层
```

## 3. 评审检查清单

新增或修改 TUI 显示逻辑时，逐项检查：

- [ ] **P1-分离**: 实时显示和数据持久化是否物理隔离？
- [ ] **P1-完整性**: 实时层的裁剪是否仅作用于显示缓冲？持久层拿到的是完整数据？
- [ ] **P2-折叠**: 超出显示空间时是否有折叠指示器？是否告知用户被隐藏的量级和查看途径？
- [ ] **P3-原地**: 流式输出是原地替换还是追加新行？
- [ ] **P4-生命周期**: 流式结束后实时层是否清空？数据是否移交到持久层？
- [ ] **刷新频率**: 实时层更新频率是否受控（<= 每帧一次）？

## 4. 反模式

| 反模式 | 问题 | 违反原则 |
|---|---|---|
| 流式时每个 token 调 `RichLog.write()` | 创建 N 行，占满屏幕 | P3 |
| 对 TranscriptView 设置 `max_lines` | 丢弃历史记录 | P1 |
| `text[-500:]` 不加指示器 | 用户不知道内容被截断 | P2 |
| 流式结束后不隐藏 StreamingText | 残留过期内容 | P4 |
| 实时层直接修改 `ctx.history` | 破坏数据完整性 | P1 |
| 每个 token 都 post_message | flooding 消息队列 | P3 (刷新频率) |
